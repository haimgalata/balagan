# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

E-commerce site for a physical Hebrew-speaking tobacco/smoking-products store ("בלאגן - מרכז הסיגריות והטבק"). React + TypeScript + Vite + Tailwind CSS + lucide-react, backed by Supabase (Postgres + Row Level Security + Auth + Storage) for the catalog and a private admin area. The build is still a static SPA — Vite just outputs `dist/`; nothing runs server-side except Supabase itself.

**"מעבר לתשלום" in `CartDrawer.tsx` navigates to a real `/checkout` page** (see "Checkout" below) that validates the cart against the database, collects delivery details, and — for **cash** — creates a real, persisted order. **Card is not wired to a payment provider yet** (the option is shown but disabled); integrating one, and everything that comes with it (payment webhooks, an Edge Function), is a future step, not something to add unprompted. Everything documented below as "the real protection" (RLS, `is_admin()`) exists precisely because the admin area and the database are real and reachable — don't reintroduce a "no backend" assumption anywhere in this codebase.

## Commands

```
npm install       # install dependencies
npm run dev       # start Vite dev server (default port 5173)
npm run build     # tsc -b (typecheck) && vite build -> dist/
npm run preview   # preview the production build
npm run test:unit # pure logic tests (*.unit.spec.ts), via Playwright's test runner, no browser needed
npm run test:e2e  # full browser suite (storefront regression + admin), Playwright + installed Chrome
```

No ESLint config exists in the repo. `supabase/` holds the database side: migrations (`supabase/migrations/000N_*.sql`, apply in order, see `supabase/README.md`), the generated seed (`supabase/seed.sql`), and one-off Node scripts run manually (never as part of `npm run build`/CI): `scripts/generate-seed.mjs` (static catalog → `seed.sql`), `scripts/verify-seed.mjs` (live database vs. the frozen baseline), `scripts/verify-order-management.mjs` (replays migrations 0001–0010 on an in-process Postgres via `npm i --no-save @electric-sql/pglite` and checks roles/transitions/restock/history/staff visibility — no project needed), `scripts/security-test.mjs` (RLS/RPC/storage behavior against a real project, admin credentials via environment variables only — never the `service_role` key, never committed).

## Architecture

### Hebrew / RTL is foundational, not a layer

`index.html` sets `<html lang="he" dir="rtl">`. Layout is expected to work via CSS logical properties (`start`/`end`, `ms-`/`me-`, `ps-`/`pe-`) rather than physical `left`/`right`, so it flips correctly for RTL without special-casing. DOM order matters for flex layout under `dir="rtl"` (first child renders on the right) — e.g. `Header.tsx` relies on this instead of manual reordering.

### Centralized theme

All brand colors live as CSS custom properties in `src/styles/theme.css` (`--color-bg`, `--color-gold`, etc., as `R G B` triplets). `tailwind.config.js` maps them to `brand.*` Tailwind colors (`bg-brand-gold`, `text-brand-text-muted`, ...). Components must use these `brand-*` classes — never hardcode hex colors. To re-theme the whole site, edit `theme.css` only.

### Catalog: read from Supabase, not hardcoded

- The storefront has **no table access** — anonymous visitors can only call the whitelisted RPC `get_storefront_catalog()` (`supabase/migrations/0004_rpc.sql`, updated by `0006`). It returns visible categories → subcategories → products, already ordered, with an explicit column whitelist (no barcode, no stock counts, no hidden rows).
- `src/storefront/lib/catalogApi.ts` fetches it with one plain `fetch` — **no `@supabase/supabase-js` in the customer bundle**; that library is admin-only (see below). `src/storefront/context/CatalogContext.tsx` (`CatalogProvider`/`useCatalog`) is the single source of the catalog: stale-while-revalidate cache (`localStorage["balagan_catalog_v1"]`), "loading" status only on a first-ever visit with nothing cached, and a bundled offline fallback (`src/storefront/data/fallbackCatalog.ts`, generated) if the network/database is unreachable and there's no cache either.
- `VITE_CATALOG_SOURCE=static` (or missing Supabase env vars) makes the storefront use the bundled fallback catalog exclusively — an instant rollback switch, and how the site behaved before Supabase existed.
- `seed-data/products.ts` / `categories.ts` are **not runtime code** — they're the one-off seed input (`scripts/generate-seed.mjs` → `supabase/seed.sql`) and the input to the generated offline fallback. Don't edit them expecting the storefront to change; edit the database (via `/admin`) instead.
- Linking convention: a product's subcategory comes from an explicit `subcategory_id` (`product.subcategorySlug` in the mapped shape); `CategorySection.tsx` groups by it, falling back to a slug derived from `brand` only when `subcategorySlug` is absent (legacy/offline data only — new products always carry an explicit subcategory, enforced by the admin form whenever the category has one).

### Business settings: read from Supabase, not hardcoded

- Same architecture as the catalog, for a different, smaller dataset: physical-store opening hours, online-order hours, minimum order, delivery fee, and a manual order-pause switch. Public RPC `get_business_settings()` (`supabase/migrations/0008_business_settings.sql`) is the only read path — `src/storefront/lib/businessSettingsApi.ts` (plain `fetch`, no supabase-js) + `src/storefront/context/BusinessSettingsContext.tsx` (`BusinessSettingsProvider`/`useBusinessSettings`) mirror `catalogApi.ts`/`CatalogContext.tsx`: stale-while-revalidate cache (`localStorage["balagan_business_settings_v1"]`) and a bundled offline fallback (`src/storefront/data/fallbackBusinessSettings.ts`) — but no "loading" status, since showing today's placeholder hours immediately (swapped for live data once fetched) is a fine first paint for a pill/banner, unlike the product catalog.
- `src/storefront/lib/scheduleStatus.ts`'s `computeScheduleStatus()`/`getIsraelNow()` turn a weekly schedule into "open now" + today's hours label, anchored explicitly to `Asia/Jerusalem` via `Intl.DateTimeFormat` — never the visitor's own device clock/timezone (a real visitor abroad, or with a wrong clock, must still see the Israel-local answer). `src/storefront/hooks/useStoreStatus.ts` (the **physical store**) and `src/storefront/hooks/useOrderStatus.ts` (**online orders**) each wrap it for their own schedule, re-ticking every 60 seconds.
- These are two clearly separate concepts, not one conflated status: `Hero.tsx`'s pill (physical-store open/closed + today's hours, in the same spot it's always been) is a button that expands `StoreHoursPanel.tsx` — the full week, today highlighted — directly beneath it. `BusinessInfoBar.tsx` (the sticky strip below `Hero`) is specifically the **online-orders** banner (green "הזמנות פתוחות" / red "הזמנות סגורות") + today's order hours + minimum order + delivery fee, all from `useOrderStatus()`. `CartDrawer.tsx`'s footer reads the same min-order/delivery-fee numbers straight from `useBusinessSettings()`, so it can never drift from the banner.
- **The manual `orders_paused` override is one-way**: `isOpen = schedule says open AND NOT orders_paused` (see `useOrderStatus.ts`). It can only force online orders closed early; there is no way to force them open outside the configured schedule — a deliberate simplicity/safety choice.

### Navigation is scroll-anchors, not a router

There's no router; it's a single page (`HomePage.tsx`). Category/subcategory links are `href="#slug"` / `href="#slug-subSlug"` hashes pointing at section ids rendered by `CategorySection.tsx` (per category) and the `id="popular"`/`id="categories"` sections in `HomePage.tsx`. `/admin` is a separate, unrelated entry point (see below) — it isn't part of this page or its hash routing.

### Cart state, pricing, and the shared-stock check

- `src/storefront/context/CartContext.tsx` (`CartProvider`/`useCart`) holds cart lines. A line is a **product + the option the customer explicitly chose** (`"unit"` or `"package"`) — nothing is ever converted between them (adding 10 loose units never becomes a package). Persistence is `src/storefront/lib/cartStorage.ts` under `localStorage["balagan_cart_v2"]`; an old `balagan_cart` (pre-option-model) is migrated once and left byte-for-byte untouched afterward.
- Prices are never stored in the cart — read live from the catalog via `src/storefront/lib/pricing.ts` (`getOptionPricing`, `getLineTotalCents`, ...), in integer agorot (no floating-point artifacts). A line whose product/option can't currently be resolved (catalog loading, hidden, package removed) stays in storage but isn't shown or priced — never destructively pruned.
- **Shared-stock quantity check** (`supabase/migrations/0007_stock_availability.sql`, `src/storefront/lib/stockApi.ts`): `addItem`/`increment` are `async` — before changing the cart they ask `check_stock_availability()` whether the product's *total* requested quantity (unit + package lines converted to the same base-unit count via `getOptionBaseUnits`/`getLineBaseUnits` in `pricing.ts`) still fits its shared stock. The RPC is boolean-only (`{product_id, available}`) and never reveals the actual stock count, `track_stock`, or whether a hidden product exists — the cart never gets to see the number, only a yes/no for the quantity it's proposing. If the check itself fails (network error), the add is refused too (**fails closed**) with its own message, rather than let an unverified quantity through. This is a UX safeguard only — it doesn't reserve or lock stock, and a future real order-processing system must still revalidate everything server-side.
- Opening the cart drawer re-checks every distinct product already in the cart in the background (catches stock that dropped after items were added) and flags a line that no longer fits (`CartLine.overLimit`) with a visible warning; the customer can still decrease/remove it, which re-checks that product immediately.
- Toasts (`Toast.tsx`, driven by `CartContext`'s `toast` state) come in two kinds: `"success"` (added) and `"warning"` (blocked — not enough stock, or the check couldn't be completed).

### Checkout (`/checkout`) — cash orders are real; card is schema-ready but not wired to a provider yet

- `src/main.tsx` loads `src/checkout/CheckoutApp.tsx` **on demand** only when the address is under `/checkout` (`src/checkout/checkoutRoute.ts` — a pure path check, same idea as `adminRoute.ts` — is the only checkout code in the customer bundle). It's a real browser navigation from `CartDrawer.tsx`'s "מעבר לתשלום" (not a modal/drawer), reached only once the cart total meets `min_order_cents` — below that the button stays disabled. `/checkout` is `noindex`.
- `CheckoutApp.tsx` wraps the same three providers `App.tsx` uses (`CatalogProvider`/`BusinessSettingsProvider`/`CartProvider`), so cart/pricing state is identical to the homepage's — unlike `src/admin/`, checkout is **not** isolated from `src/storefront/`; it deliberately reuses `CartContext`, `CatalogContext`, `pricing.ts`, `stockApi.ts`, and the shared `CartLineRow.tsx` component (also used by `CartDrawer.tsx`, so both editing surfaces look and behave identically). `CheckoutPage.tsx` gates its own render on `CatalogContext`'s `status` (not just `lines.length`) — on a fresh `/checkout` visit in `supabase` mode the catalog fetch is still in flight, so `lines` is transiently empty even with a real cart; redirecting home on that would be wrong.
- **No durable "checkout session."** `src/checkout/useCheckoutValidation.ts` re-validates against the database at the moments that matter instead — on mount, on tab refocus, and once more right before the final submit — via `CatalogContext`'s on-demand `refresh()` (bypasses the stale-while-revalidate cache) plus a direct `check_stock_availability()` call. A price change is shown inline but never blocks (the line already re-prices live once the catalog updates); a stock shortfall blocks only that line, reusing the cart's own `overLimit` flag; a network/RPC failure fails **closed** (`phase: "failed"`, with a retry action) — checkout never lets the customer proceed on an unverified cart.
- `DetailsForm.tsx` collects first/last name, phone (required), email (optional — for future order confirmations only), a full delivery address, and a payment method, with client-side validation only — the server (`create_order()`, see below) re-validates everything itself and is the only thing that actually decides whether an order is created.
- **Delivery is Netivot-only today, enforced in the form AND the database**: the city field is fixed to `NETIVOT_CITY_NAME` (not editable — see `data/netivotStreets.ts`) and the street field (`StreetField.tsx`, a small hand-rolled combobox — no new UI dependency) only accepts an exact match from `NETIVOT_STREETS`, a static list of Netivot's ~200 official streets sourced once from data.gov.il's street registry (the file's header has the exact query to refresh it if the delivery area or its streets ever change); `create_order()` rejects any other city regardless of what the client sends. House number is required; entrance/floor/apartment/intercom code are optional. Two required checkboxes — age confirmation (18+ at delivery, ID checked) and site-terms acceptance — are deliberately separate from each other and from any future marketing-consent checkbox (not implemented yet, and must never be merged into these).
- **Real orders**: submitting calls `create_order()` (`supabase/migrations/0009_orders.sql`) via `src/checkout/lib/ordersApi.ts` (plain `fetch`, same no-supabase-js-in-customer-bundle pattern as `catalogApi.ts`/`stockApi.ts`), with a client-generated idempotency key (`src/checkout/lib/idempotency.ts`, persisted in `sessionStorage` so a refresh/retry can't create a duplicate order). A **cash** order comes back `confirmed` immediately (stock already permanently deducted) and the customer sees a real order number; the cart is cleared (`CartContext.clearCart`) only once the server confirms the order actually exists. **Card is collected in the form but shown disabled ("בקרוב")** — no payment provider is integrated yet, even though `create_order()` fully supports `payment_method: 'card'` (reserves stock, creates a `payment_attempts` row) so no schema work will be needed when one is chosen.
- Payment-provider integration (an Edge Function for the redirect + a signature-verified webhook calling `confirm_payment()`), and automatic reservation-expiry scheduling are future steps (the admin's orders view now exists — see "Admin area" → Orders) — see `supabase/README.md`'s "Orders" section for the full design.

### Admin area (`/admin`) — real protection is in the database, not the route

- `src/main.tsx` loads `src/admin/AdminApp.tsx` **on demand** only when the address is under `/admin` (`src/admin/adminRoute.ts` — a pure path check, no React/Supabase — is the *only* admin code in the customer bundle; a real-build test, `tests/admin/auth/bundle.unit.spec.ts`, enforces this). Nothing on the customer site links to `/admin`; it's `noindex`.
- Authentication is Supabase Auth (email + password; public sign-ups must stay disabled in the dashboard). Authorization is **independent of authentication**: an `admin_users` allow-list checked by `is_admin()` (`supabase/migrations/0002_rls.sql`) — being logged in is never enough. Every table has default-deny Row Level Security with policies gated on `is_admin()`; the admin route guard (`src/admin/useAdminSession.ts`) is UX only. 60-minute idle logout — **owner only**.
- **Two roles (migration `0010`)**: `admin_users.role` is `'owner'` (default — the original admin) or `'staff'` (the shared store-terminal account; order handling only). `is_admin()` now means **owner only**, so every existing catalog/settings/payment policy is unchanged and denies staff automatically; `is_staff()` = any back-office user; `get_my_role()` is what the admin app asks after login (UX only — `AdminShell.tsx` shows staff just "הזמנות" and bounces them there from any other `/admin` path, but the database is what refuses). The staff account is exempt from idle logout (it lives on the order terminal). Roles are plain text + CHECK, deliberately extensible; individual employee accounts later need no redesign (history already records the acting account). MFA, when enabled, applies to owners only. Never re-run an old copy of `0002` that lacks the `au.role = 'owner'` line — it would widen `is_admin()` to staff.
- **MFA is deferred, not implemented.** `is_admin()` has a commented-out line requiring an `aal2` (MFA-verified) session — flip it on (and re-run `0002_rls.sql`) only once the admin UI has a TOTP-enrollment screen (not built yet), and only when the site is about to go live to real customers. Enabling the line before that screen exists would lock the admin out of writes.
- **Categories** (`/admin/categories`, `src/admin/categories/*`, migration `0005`): Hebrew/English names, visibility, up/down ordering, add/delete (delete blocked while something still holds products/subcategories — hide instead). A slug is chosen once at creation and locked afterward (it's the public `#anchor`).
- **Products** (`/admin/products`, `src/admin/products/*`, migration `0006`): two tabs — a searchable/filterable/paginated list (find, add, edit, hide, real permanent delete with a two-step confirm — nothing else references a product, unlike categories) and a separate ordering view (pick one category+subcategory group, up/down; a category with no subcategories skips straight to its one group). **Shared inventory**: one `stock_base_units` count per product plus `track_stock`; `unit_in_stock`/`package_in_stock` are `GENERATED` columns (`stock_base_units >= required OR NOT track_stock`, AND the independent manual `unit_available`/`package_available` switches) — a unit and its package draw from the *same* pool, not separate counters. A product's photo is always optional, in create AND in edit: `ProductImagePicker.tsx` (create — stages a file locally, no product id exists yet) and `ImageUploader.tsx` (edit — uploads and saves immediately, independently of the rest of the form) both funnel through the same `uploadProductImage`/`updateProduct` in `productsApi.ts`; a create's image step failing never rolls back the product itself (see `ProductsListTab.submitCreate`).
- **Orders** (`/admin/orders`, `src/admin/orders/*`, migration `0010`): the operational screen — **Active board** at `/admin/orders` (lanes: חדשה `confirmed` → בהכנה `preparing` → בדרך `out_for_delivery`, then `completed`; today's finished orders in a collapsible list; a "needs attention" strip for orders cancelled after dispatch whose stock hasn't been confirmed back and for paid-but-dead card orders), **history & search** at `/admin/orders/history` (owner: filters over everything; staff: search box only, database-limited to open orders + the last 7 days), and a deep link `/admin/orders/<order_number>`. One shared `OrderDetailContent`/`OrderActionBar` serve the board cards, the drawers and the deep link. **All order changes are RPCs** — `transition_order(order, expected_status, to_status, reason)` (locks the row, `STALE_STATUS` when another terminal moved it first, allowed-transition map, one step back for staff / reopening `completed` owner-only, mandatory cancel reason, cash marked `paid` on completion) and `resolve_stock_return()` — because `authenticated` has **no INSERT/UPDATE/DELETE on `orders`/`order_items`** anymore. Cancel before dispatch restores stock automatically; cancel while `out_for_delivery` sets `stock_return_status='pending_return'` and stock stays out until someone confirms the goods are back (owner may write off). `order_status_events` (trigger-written, append-only) is the full timeline with the acting account. Realtime is an accelerator only: `useActiveOrders.ts` re-queries on subscribe / every 30 s / tab-visible / network-back and treats a `postgres_changes` event as "reload now" (payload ignored); `useOrderAlerts.ts` derives the chime from *state* (any unannounced `confirmed` order, repeating every 30 s until accepted, mute available, announced-ids in `localStorage`) and needs a user gesture ("התחלת משמרת") after every page load for audio + screen wake lock. Pure logic (labels, transitions offered, search-filter building — never interpolate raw text into a PostgREST `or=`, Israel-day boundaries) is in `orderModel.ts`, unit-tested. Card payments are still not wired; nothing in order management assumes receipts/accounting.
- **Customers** (`/admin/customers`, `src/admin/customers/*`, migration `0013`, **owner only** — hidden from staff, who are redirected to Orders): headline numbers (members, joined in 30 days, ever ordered, reachable by SMS / by e-mail, withdrew consent, deleted), a searchable (name / phone in any local format / e-mail), consent-filterable, paginated member list, and three audience exports as CSV — `sms` and `email` (only members whose LATEST marketing consent covers that channel; e-mail also needs an address) and `suppression` (the do-not-contact list: withdrawn + deleted). **The owner has no direct table access to customer data**: everything goes through `admin_customer_stats()` / `admin_list_customers()` / `admin_export_audience()`, each re-checking `is_admin()`; every export is logged (who, what, how many) in `customer_exports`, which nothing can read through the API. The CSV (`customersModel.ts`, unit-tested) is UTF-8 with a BOM for Excel Hebrew, CRLF, English column names for mailing/SMS tools, every cell quoted, and cells a spreadsheet would run as a formula (customer-typed `=…`) get a leading apostrophe. Confirmation before every export. Deleted members are never listed and keep only a phone number on the suppression list.
- **Business Settings** (`/admin/settings`, `src/admin/settings/*`, migration `0008`): two sections — physical-store weekly hours, and everything about online orders (weekly hours, minimum order, delivery fee, a manual pause switch that's a one-way override — see below). No drawer; each section is a plain form with an explicit "שמירה", except the pause switch, which applies immediately (an emergency control shouldn't wait on an unrelated unsaved edit in the same form).

### Club accounts (registered customer = Balagan Club member) — Phases 1–3: login shell + checkout integration + personal area, OFF in production

- **Product rules (owner-decided):** guests can always order; registering makes you a club member (no non-member accounts); joining needs ONE mandatory checkbox (21+ AND consent to written marketing by SMS/email — `src/account/clubConsent.ts`, wording needs lawyer sign-off); every ORDER still needs the 18+ checkbox, members included; terms once per version; registration/login happens BEFORE payment (never a post-order prompt); guest details are remembered only on the same device. Full plan: `C:UsersUSER.claudeplanspasted-content-id-dc37-i-want-elegant-ullman.md` (rev. 2), data layer in migration `0012`, permission audit in `docs/CUSTOMER_PERMISSIONS_AUDIT.md`.
- **The login provider is deliberately undecided.** `src/account/types.ts` defines the `CustomerAuth` seam (sendCode / verifyCode / getSession / signOut → a bearer token whose `auth.uid()` the database knows). Everything after login (`CustomerSessionContext.tsx`, `memberApi.ts` → `get_my_customer`/`join_club`, `LoginPanel`/`JoinStep`/`AccountPanel`) depends only on that. The only adapter is the TEST-ONLY `auth/mockAuth.ts` (code `123456`). A real SMS/OTP adapter = one new file + one branch in `auth/loadCustomerAuth.ts` + one value of the build constant; the database never trusts a client-sent phone (it reads `auth.users.phone`).
- **Build switch:** `__CUSTOMER_AUTH__` (compile-time constant from `VITE_CUSTOMER_AUTH`, `vite.config.ts`; `"off"` unless `mock`). **Production = off**: the account drawer is the unchanged inert "coming soon" panel, no account code is in the bundle, the homepage makes no new requests. Never set `VITE_CUSTOMER_AUTH=mock` for a real deploy. Do not enable public sign-ups or a real adapter before the remaining steps in `docs/CUSTOMER_PERMISSIONS_AUDIT.md` are done.
- **Bundle rules** (`tests/admin/auth/bundle.unit.spec.ts` enforces them): the only account code in the main bundle is `AccountDrawer.tsx` + `src/account/memberHint.ts` (a tiny `localStorage["balagan_member_hint_v1"]` = `{firstName}` note so the header can greet a member; no token, no phone, never trusted). Everything else is the lazy `AccountPanel` chunk; no `@supabase/supabase-js` and no `auth/v1` anywhere in customer code. The login session itself lives under its own key (`balagan-customer-auth`), separate from the admin's.
- **Tests:** `tests/account/*` run only in the dedicated `account` Playwright variant (port 5194, mock login + stubbed database, `playwright.config.ts`), never in static/supabase/live. Phone helpers (`src/storefront/lib/phone.ts`) are pinned to the SQL `normalize_il_phone()` by identical examples.
- **Checkout integration (Phase 2):** `src/checkout/club.tsx` is the ONLY seam between checkout and the club code (`ClubProvider`/`useClub`/`ClubIdentity`/`useClubAddresses` — all compile to no-ops when `__CUSTOMER_AUTH__` is `"off"`, so a production checkout is the plain guest checkout; import club things from there, never from `@/account/*` directly). With a login adapter: `CheckoutIdentity.tsx` shows the "sign in / join — or continue as guest" card ABOVE the form (login/registration before payment; the login reuses `AccountPanelBody` in a drawer), the form is held back until a restored session + the member's saved addresses are known, then `DetailsForm` gets the member's profile (name/email prefilled, phone locked to the verified one, saved-address card with "שינוי"/"כתובת חדשה", terms checkbox hidden once `customers.terms_version === CURRENT_TERMS_VERSION` (`lib/terms.ts`) — **the 18+ checkbox is always required**). `createOrder` sends the member's bearer token (`memberAccessToken`) so the database attaches the order via `auth.uid()`; if the profile couldn't be loaded or the token can't be had, the order goes out as an ordinary anonymous guest order (claimed by phone later). After a member order `refreshProfile()` re-reads the profile (the order taught it the name) and the header hint. A saved address is created/updated BY THE DATABASE (migration 0012 trigger), never by the client.
- **Guest memory (all builds, owner decision):** after a successful GUEST order the delivery details (`lib/guestMemory.ts`: names, phone, email, street/house/entrance/floor/apartment/intercom, notes — never the age/terms confirmations or payment method) are kept in `localStorage["balagan_guest_details_v1"]` and prefill the next checkout on that browser; a visible note says so and "מחיקת הפרטים השמורים" forgets them; they are cleared when the visitor becomes a member. They go nowhere except inside an order the guest submits.
- **Personal area (Phase 3, `/account`):** `src/account/accountRoute.ts` (pure path check, imports nothing) + a branch in `src/main.tsx` gated on `__CUSTOMER_AUTH__ !== "off"` load `src/account/AccountApp.tsx` on demand — in a build without a club login the branch and the whole page are removed and `/account` is just the homepage. Deliberately small, four tabs in `src/account/page/`: **ההזמנות שלי** (`get_my_orders()`; "הזמן שוב" re-adds items through the ordinary `CartContext.addItem` — which now resolves `true` only when the item was really added — so the shared-stock check and live prices still apply; skipped items are named; nothing is ordered, the customer goes on to checkout), **כתובות** (list/add/edit/delete/"make default" straight on `customer_addresses` via row-level security; "default" = most recently used, max 5, a duplicate is a 409), **הפרטים שלי** (name + e-mail only — the database grants no write access to phone/terms/status; phone shown locked), **העדפות** (marketing consent on/off + SMS/e-mail channels through `set_marketing_consent()`, sign out, "delete my account" with a confirmation → `delete_my_account()`). Withdrawing marketing never deletes the account. `useMemberRun` runs every request with a fresh token and signs the member out on `UNAUTHENTICATED`. Non-members visiting `/account` get the same login panel as the drawer and checkout. Pure display logic (status labels, Israel-time dates, summaries) is in `orderLabels.ts` (unit-tested).
- **Not built yet:** terms + privacy pages (the checkout terms text is still a plain span), a persisted `orderId` on the success screen, a real SMS/OTP login adapter, receipts.

### Database

`supabase/migrations/0001` through `0010` (apply in order; `0010` = owner/staff roles, the order lifecycle + `order_status_events` + `transition_order()`/`resolve_stock_return()`, orders read-only via the table API, Realtime on `orders` — apply it **before** deploying an admin build that calls `get_my_role()`; each file's header says what it does and whether it's re-runnable). High-level: `0001` schema, `0002` RLS + `is_admin()`, `0003` the `product-images` storage bucket, `0004` the public catalog RPC, `0005` admin Categories support, `0006` admin Products support (shared inventory), `0007` the cart's stock-availability RPC, `0008` `business_hours`/`business_settings` + the public `get_business_settings()` RPC, `0009` `orders`/`order_items`/`payment_attempts`/`payment_events` + stock reservation + `create_order()`/`get_order_status()`/`confirm_payment()` (see "Checkout" above and `supabase/README.md`'s "Orders" section for the full design). `0011` = customer-permission hardening (see `docs/CUSTOMER_PERMISSIONS_AUDIT.md`: `order_status_events` is back-office only; customers never read `orders`/`order_items` through the table API), `0013` = the owner's customer list/stats/audience exports (owner-only functions, audited exports — see "Customers" under Admin area), `0012` = Balagan Club data layer (registered customer == club member; `customers`/`customer_consents`/`customer_addresses`, `join_club()` etc. — database side only so far, no customer UI/auth yet, public sign-ups still OFF until the audit's remaining steps are done). `supabase/README.md` has apply/verify instructions for each. Product ids stay `text` (`"1"`…`"148"` with intentional gaps, inherited from the pre-migration static catalog); new products get `149, 150, …` from `product_id_seq`. Order ids are `uuid` (non-enumerable, since an order carries a name/address unlike the public catalog) with a separate sequential `order_number` for admin/phone use.

### Shared UI primitives

- `src/shared/ui/Button.tsx` — the only place button variant styling (`primary`/`secondary`/`outline`/`ghost`) is defined.
- `src/shared/ui/Drawer.tsx` — shared slide-in panel (backdrop, Escape-to-close, scroll lock, transform-based slide) used by `CartDrawer.tsx`, `AccountDrawer.tsx`, and the admin's `CategoryFormDrawer.tsx`/`ProductFormDrawer.tsx`. Extend this rather than building a second drawer implementation. These two files are the only code shared between the storefront and the admin app — everything else in `src/storefront/` is customer-only and everything in `src/admin/` is admin-only (see `docs/PROJECT_STRUCTURE.md`).

### Known gotcha: off-canvas panels and horizontal scroll

`Drawer.tsx` hides panels via `-translate-x-full`/`translate-x-full` while keeping them in the DOM. Chrome still counts a translated-off-screen fixed/absolute element toward `document.documentElement.scrollWidth`, which silently adds a phantom horizontal scrollbar. This is why `src/index.css` sets `overflow-x: hidden` on `html, body` — don't remove it, and apply the same fix if you add another off-canvas element.

### Known gotcha: testing from a real phone over `npm run dev`

`npm run dev` serves plain HTTP with no TLS. Opening it from a real phone over the LAN by IP address (`http://192.168.x.x:5173`) is **not a secure context** (only `https:`/`localhost`/`127.0.0.1` count) — desktop and even DevTools' mobile emulation don't hit this, because both stay on `localhost`. Anything that depends on a secure-context-gated browser API (e.g. `crypto.randomUUID()` — this bit `uploadProductImage` in `productsApi.ts` once; it now uses a plain non-crypto id) will silently misbehave ONLY in this specific real-device-over-LAN case, never in production (a real deploy is HTTPS). If something "works on desktop but not on a real phone" during dev, check `window.isSecureContext` on the phone before assuming the bug is about the phone, the file, or the network.

### Path alias

`@/` resolves to `src/` (configured in both `vite.config.ts` and `tsconfig.app.json`). Under `src/`, code is split into `src/storefront/` (customer-facing: components, context, hooks, lib, pages, types, data), `src/checkout/` (the `/checkout` app, reusing `src/storefront/`'s context/lib), `src/admin/` (the private `/admin` app, unchanged internally), and `src/shared/ui/` (the two primitives above, used by both storefront and admin). ### Environment variables and deploying

`.env.example` lists what's needed: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (the anon/publishable key only — **the `service_role` key must never appear anywhere in this project**, in code, an env file, or a commit), and `VITE_CATALOG_SOURCE`. Vite bakes these into the build, so whatever host serves the production build needs the same variables set in its build settings.

No hosting provider is configured in this repo yet (no `netlify.toml`/`vercel.json`/etc.). Whichever static host is eventually chosen must be told to serve `index.html` for unknown paths (an "SPA fallback" / rewrite rule) — without it, a customer directly navigating or refreshing on `/admin` gets the host's own 404 instead of the app. One-line reference for when a host is picked (not yet added as a file):
- **Netlify** (`netlify.toml`): `[[redirects]]` with `from = "/*"`, `to = "/index.html"`, `status = 200`.
- **Vercel** (`vercel.json`): `"rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]`.
- **Cloudflare Pages**: SPA fallback is automatic for a Vite build with no extra config.
